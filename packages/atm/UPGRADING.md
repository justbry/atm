# Upgrading atm

## Moving to 0.6.0 from 0.5.0

A minor release: it adds the pieces that turn the handler's events into financial reports, and one handler change that adds events. Nothing is removed. What a caller sees:

- **The handler writes more events per delivery.** An `invoice.paid` now also makes a `payment.succeeded`, a `charge.refunded` of a handled invoice a `payment.refunded`, and a `payout.paid` event a `payout.paid` (see "Stripe fees, refunds and payouts in the log" below). A test or a caller that counted events per delivery sees more, and an endpoint must subscribe to `payout.paid` to book payouts.
- **New exports:** `shipOutbox`, `planOutbox`, `outboxStatus`, `recordEngineCommand`, `recordLapse`, `reconcile`, and the types that go with them.
- **New CLI commands:** `atm ship`, `atm report`, `atm reconcile`; `atm journal` and `atm ship` take `--json` and exit 2 on an error that is not a conflict.
- **New optional handler dependency:** `paymentFee(event)`, the Stripe fee of a payment (without it the payment is booked gross, with `fee_known: false`).
- **A menu with colliding feature ids is now refused, and this one is a break.** A credit's commodity is its feature id in capitals with every non-letter dropped, so `light-60` and `light-90` were both `LIGHT` and their credits added up in one hledger balance, and an id with no letter (`2026`) threw when its first credit was journaled. `validateMenu` now returns `{ ok: false, problems: ["features.1.id"], messages: ["feature ids \"light-60\" and \"light-90\" both become the credit commodity LIGHT ..."] }` (`messages` is new and optional) and `menuCatalogRows` throws the same sentence, so a caller that builds its catalog from a stored menu on each webhook fails on a colliding one. `commodityOf` is unchanged, so journals already built keep their commodities (a merged balance in one cannot be split afterwards). Before upgrading, run `validateMenu` over every stored menu version, the published ones too: the family service's menu editor names a new credit `credit`, then `credit-2` (`packages/web/src/lib/school-billing/validate.ts`, `blankFeature`), which are both `CREDIT`, and a published version is not edited in place, so a school that has one needs a new version with ids whose letters differ (the family service's `docs/features/school-billing.md` says a member keeps the version they bought, so that older version would still be refused when its catalog is built). This release does not touch `buzz-school`, and the family service, still on `atm-v0.3.0`, does not call `validateMenu`.
- **`drawnAfter` is now defined at the lapse instant.** `drawnAfter(t)` is the units drawn strictly after `t`, and `lapseAlertEvents` calls it once per lapse instant `I`, with `I - 1` (it counts a draw at exactly `I`), and adds that one number to both totals it compares. In 0.4.0 and 0.5.0 it was called with `I - 1` for the total before the lapse and `I` for the total at it, so a draw at exactly `I` was added back on one side only and could make a false `credit.depleted`. A caller that returns draws by time needs no change; one that ignored the argument gets the same answers.
- **What the family service does, in order,** is the first section below. This release changes nothing in `buzz-school`.

### Moving the family service onto the handler, the shipper and the reports

The family service still grants with its own rules (`packages/family-service/src/school-billing/grant.ts`) and nothing ships its outbox. **This change does not touch buzz-school**; it makes atm's side exact, and `README.md` ("Running it") has the recipe with the real paths. What the family service changes, in order:

1. **Pin the atm release that contains this**, in `packages/family-service/package.json` (it is at `atm-v0.3.0` there; the handler, `env`, the quantity rules and `shipOutbox` are later releases), and run `bun install` for `bun.lock`. This change adds `outboxStatus` (library) and the `atm report` command, and changes two exit codes of `atm ship` (below).
2. **Move existing members onto atm's rows** with `grantsStateFromCallerRows` from `school_memberships` and `school_credit_lots` (`packages/family-service/src/school-billing/subject.ts` and `store.ts` read them), as the adoption section below describes, before the first event reaches the handler.
3. **Create the handler's tables** (`HANDLER_DDL`) in the service's SQLite file (`DB_PATH`), as a migration in `packages/family-service/migrations/` (the statements are `IF NOT EXISTS`; `test/schema-portable.test.ts` there checks migrations parse under Litestream), and write a `SqlDatabase` over the service's `Db` port (`src/db/port.ts`; the handler's `transaction` should take the write lock at `BEGIN`, as `bunSqlite` does).
4. **Mount the handler** in `src/routes/school-billing.ts`'s `/hooks/stripe/school` route: keep its school lookup and secret opening, and replace the signature check, the `school_stripe_events` claim and `handleSchoolEvent` (`src/school-billing/webhook.ts`, `grant.ts`, `apply.ts`) by `handleStripeWebhook`, passing `env` from `billingKeyMode` and a `context` built from `school_billing_menus` (`menu.ts`, `store.ts`). Recreate each school's Stripe endpoint with `api_version: "2025-10-29.clover"` (`src/school-billing/connect.ts`), subscribed to the events listed under "Moving to 0.3.0".
5. **Register the shipper** as a job in the registry (`src/jobs/`, started from `src/server.ts`): `shipOutbox` per school with outbox rows, every 5 minutes, into a folder on the volume, logging each conflict as an error line. A health check reads `outboxStatus` (an `ops` command beside `backup-status` in `src/ops/cli.ts`, or a monitor check beside `litestream_fresh` in `packages/scripts/ci-watchdog/prod-monitor.ts`).
6. **Back up the ledger folder**; Litestream replicates the database file only.
7. **Run `atm report` monthly** off the machine (bun, hledger and an atm checkout), on a copy of the folder.

**`atm ship`, `atm journal` and `atm report` exit codes.** `atm ship` exits 0 done, 1 a conflict, 2 any other error with one line and no stack trace. A `--root` that is not an existing folder and a `--school` with no rows in the outbox are exit 2, so a wrapper that alerts on 1 means a conflict. A missing or unknown option exits 2 too. An outbox with no row at all (no school has had an event) now ships nothing and exits 0; a `--school` that is not among the schools that do have rows is still refused. `--json` (on `ship` and `journal`) prints one line: see `README.md`. `atm journal` printed a stack trace and exited 1 on an error (for example a school with no events); it now prints one line and exits 2.

### Stripe fees, refunds and payouts in the log

A log made by `handleStripeEvent` or the reference handler used to hold only credit events: `hledger is` and `bs` over it showed no money at all. It now holds the money lines too (`README.md`, "Money lines"). Caller changes:

- **Subscribe the endpoint to `payout.paid`** (a ninth event; the other eight are listed under "Events to subscribe to" below). Without it no payout is booked and the cash stays in `assets:stripe`. Not needed, and ignored if sent: `payout.failed`, `payout.created`, `payout.reconciliation_completed`. A payout carries no family or school, so it is booked to `deps.schoolId`: keep one endpoint per school, on the school's own Stripe account.
- **Pass the fee, if you want it booked.** Add `paymentFee(event)` to `WebhookDeps` (or `fee` to `StripeEventInput`): the Stripe fee in cents of the payment an `invoice.paid` is, which is the `fee` of its charge's balance transaction (invoice payment, then its charge, then `balance_transaction`; for a direct charge on a connected account, as that account). No webhook event carries it. The handler is synchronous, so read Stripe before calling it and answer from what you hold. Without it the payment is booked at its gross amount with no fee line, and its payload says `fee_known: false`. A fee not known at the first delivery is not added later.
- **Every `invoice.paid` now makes a `payment.succeeded`, and every `charge.refunded` of a handled invoice a `payment.refunded`.** A test that counted the events of an invoice or a refund sees one more. `handleStripeEvent` gives the refund's line again when it is handled again (same id and idem; the outbox drops it), so its `events` is no longer empty on that replay; the rows still are `null`.
- **Shapes.** The `charge.refunded` mapping reads `currency` and `previous_attributes.amount_refunded`; there is a `payout.paid` mapping and a `StripePayout` fact. `StripeEventInput` has two optional fields, `fee` and `school` (needed for a payout).
- **A refund line now names its charge, payment intent and invoice, so `reconcile` can pair it.** The handler's `payment.refunded` is labelled with the Stripe event id (`evt_...`; a `charge.refunded` has no refund id), and `reconcile` used to report every one as `missing_in_stripe` beside a `missing_in_log` for Stripe's `re_...`. The payload now also has the optional `charge`, `payment_intent`, `invoice` and `amount_refunded`, and `reconcile` pairs such a refund with Stripe's refunds of the same payment and amount (`StripeRefundRecord` has optional `charge` and `payment_intent`; `stripe refunds list` prints both, so `refunds.json` needs no change). Nothing to change in a caller that uses the handler. A log already written keeps `evt_...` refunds without the fields: those still cannot be paired and are reported. A family service that books its own refunds should carry the Stripe refund id (`re_...`) as `payload.id`, which `reconcile` still matches by id, or the same fields.
- Not built: money lines for disputes, a reversal of a payout that fails after `payout.paid`, and a fee added after the payment was booked.

### Shipping the outbox to a folder

Additive: nothing changes for a caller that does not call it. Until now the handler's events stayed in `ledger_outbox` and nothing wrote the files `atm journal` reads. New exports:

- `shipOutbox({ db, store, school, nowMs })` takes the school's rows with `shipped_at IS NULL` and puts one object per event date, `schools/<school>/events/date=YYYY-MM-DD/batch-<first id>-<16 hex of the text's sha256>.jsonl` (the bodies, one per line, in id order, as the handler stored them), with `putOnce`. An equal object already there counts as shipped; different bytes under the key is a `conflicts` entry and the rows stay unshipped (it never overwrites); so is a day that already has a `day.jsonl`, because the reader keeps only `late-*` beside it. It then sets `batch_key` and `shipped_at` on those rows in one transaction. It returns `{ batches, conflicts, shipped }`. It throws, before any put and for the whole school, on a row the reader could not read or would collapse (a date that is not `YYYY-MM-DD`, an id with a character other than letters, digits, `_` and `-`, a body that is not one line of a JSON object carrying the row's own `id`, `idem` and `date`); the handler never writes one, so this is a guard against a hand-edited database, since the log is create-only and a bad object could not be taken back. The `day.jsonl` check and the put are two calls: a `day.jsonl` that appears between them is not caught (nothing writes one yet). It works on any `Store`; only `FolderStore` is tested. `planOutbox({ school, rows })` is the pure plan it runs, with the types `OutboxRow`, `OutboxBatch`, `ShipOutboxInput` and `ShipOutboxResult`.
- **What a family-service caller changes.** After the handler has answered (or on a timer, or from a cron), call `shipOutbox` with the same `SqlDatabase` the handler uses and a store for the log. Any number of runs, and more than one shipper, are safe: a rerun finds nothing, a crash between the put and the mark is repaired by the next run when no row arrived for that day in between (same rows, same key, same bytes; if one did, the rerun puts a second, overlapping batch and the first stays, its events dropped by the reader by `idem`), and two shippers on the same rows write one file. Alert on a non-empty `conflicts`. Then `atm journal` (or `journalMonth`) over the folder builds the journals.
- `atm ship --db <handler sqlite file> --root <folder> --school <id>` runs it from a shell (Bun only, as the rest of the CLI; it opens the file read-write and waits up to 5 s for the handler's lock). It exits 1 on a conflict, on a `--root` that is not an existing folder (create it first: a typo in it would otherwise make a new folder and mark every row shipped into it), and on a `--school` with no rows in the outbox (it names the schools that have some).
- Not built: R2 batches (the call works against `R2Store`, untested there), the `day.jsonl` combine, the signed manifest and Parquet. A batch is named `batch-*`, never `day.jsonl` or `late-*`. The shipper does not write into a day that already has a `day.jsonl` (a `conflicts` entry), since the reader would not read the batch; once the combine exists, it has to decide how a day combined after its rows shipped takes later rows (`late-*`).

### Logging the family service's own commands

Additive: nothing changes for a caller that does not call it, and the handler writes what it wrote. New exports: `recordEngineCommand({ db, mutation, before, context, logsEveryCommand? })` and `recordLapse({ db, state, featureOf, feature, atMs, tz, drawnAfter?, labels? })`, which append to the same `ledger_outbox` the handler uses (`ON CONFLICT (school_id, idem) DO NOTHING`), so a log shipped by `atm ship` holds what the family service ran and `replayEvents` can replay it.

- **What the family service changes.** After every engine command it runs (hold, finalize, spend, refund) and in the expiry cron, call these with the same `SqlDatabase`, inside the transaction that writes the subject's rows, after the revision check: run the command, write the rows, record the events. They open no transaction. Give each command a `commandId` of its own, unique across the school: one that is already in the outbox for another subject or revision (a booking's id used for both its hold and its finalize, a retry that ran the engine again after the rows committed) makes `recordEngineCommand` throw, so the transaction rolls back, rather than drop the event while the rows change. Recording the same mutation twice adds no second event.
- **What it records.** The whole mutation on every event, a `plan.changed` for a command that moves no credits, nothing for a null or rejected result (which change no rows either). The `context` carries what the postings need that the mutation does not (`feature`, `service`, `as`, `reason`, `settleAs`, `lowCreditThreshold`, ...); the school is the mutation's `identity.orgId`.
- **`payload.complete`.** Left out unless `logsEveryCommand: true`; set it only if every engine command for the subject is recorded. A replay reads it only for commands named `<ULID>:<step>`.
- Not built: commands that move several features (`reset`, `applyBillingPlan`) are not cut by feature and plan here, and `recordEngineCommand` throws for them; a family service does not run them (the handler does). A command that makes new rollover rows (the engine's random ids) is not recorded.

### Reconciling the log with Stripe

Additive: nothing changes for a caller that does not call it. `reconcile({ events, stripe, period, timeZone?, mode? })` and `atm reconcile --root <folder> --school <id> --month YYYY-MM --stripe <dir>` compare a school's events with the arrays `stripe <resource> list` prints (invoices, refunds, disputes, payouts, balance transactions) and return typed differences (`missing_in_log`, `missing_in_stripe`, `amount_differs`, `duplicate_in_log`, `outcome_differs`, `period_differs`, `not_in_log`). The CLI exits 0 when nothing differs, 1 when something does and 2 for input it cannot use, which includes a `--stripe` folder missing any of the five files (the result is still printed; those checks did not run).

- **What a caller changes.** To be told of a lost or wrong event, run the `stripe` commands for the school's connected account (README, "Reconciling with Stripe") and call `reconcile` or `atm reconcile` nightly; alert when `differences` is not empty (or the exit is 1). Nothing is written.
- **It reads the log's conventions.** An event is matched by Stripe's id in `payload.id` (an invoice id on `payment.succeeded`, a refund `re_` on `payment.refunded`, a dispute `dp_` on `payment.disputed` and `dispute.closed`, a payout `po_` on `payout.paid`), as `schema/payload/` describes. A log whose events carry another id reports every one as missing, except a refund event the handler made: its id is the Stripe event's `evt_…`, and it names its charge and payment intent, so `reconcile` pairs it with Stripe's refunds of the same payment by amount (see "A refund line now names its charge, payment intent and invoice" above).
- **A log without fees or payouts reports them once**: one `not_in_log` record for the fees (or the payouts) of the period, not one per payment; the net is then compared before fees.
- **Not built**: no Stripe call (the caller fetches), no schedule, no per-payment fee match (a charge cannot be tied to its invoice on API `2025-10-29.clover`), no alert delivery.

## Moving to 0.5.0 from 0.4.0

A review of 0.4.0 found four ways it could grant or alert wrongly, and five smaller problems. This is a minor release, not a patch, because the handler now refuses a test-mode event sent to a default (`env: "live"`) handler. Two of the fixes change what a caller has to do (`drawnAfter`, and `env: "test"` on a test endpoint):

- **The lapse alert needs `drawnAfter`.** `lapseAlertEvents` takes a new required `drawnAfter(instantMs)`: the units of the feature the holder drew after that instant and up to `atMs`, from the cron's ledger or journal (draws only). A signature change to a function released a day ago that nothing calls yet. Without it a late cron judged a past lapse on today's balances and made a false `credit.depleted` when the family had drawn from another live row since. Pass `() => 0` only when the state is as of the lapse.
- **The engine path does not throw on a malformed proration.** `invoiceToCommands` (so the webhook) reads Stripe's lines through unchecked cores and does what 0.3.0 did, so a malformed value can no longer make the handler answer 500 and Stripe retry for days. The public `prorationPair` and `raiseUnits` still throw, but `prorationPair` checks only the lines it uses: the chosen charge and its credit, and `amount` and `periodStart` on every tier proration line (the selection compares them). A stale older pair with a bad quantity or `periodEnd` no longer makes a valid raise throw.
- **The handler refuses a `livemode` that disagrees with `env`.** An event whose `livemode` is a boolean other than `env === "live"` is answered 422 `livemode_mismatch` before any claim, and nothing is written. A test-mode endpoint must now pass `env: "test"` (the default is `"live"`, so a test-mode event sent to a default handler is refused, where 0.4.0 wrote it to the `|live|` subject). An event with no `livemode` is not refused. `handleStripeEvent` is not checked: it never sees the endpoint.
- **Same-instant ordering.** `lapseAlertEvents` books its `credit.depleted` at `revision + 1`: pass the revision you give the `credit.expired` events of the instant (the highest, if they differ) and the alert sorts after all of them in replay, the journal and the month files; its `eventMs` is still the instant and its idem is unchanged. A revision that is not a whole number, or is 16777215 or more, throws. In 0.4.0 the two shared time and revision and their order was a hash tie.
- **`credit.depleted` has two exclusive shapes.** With `cause: "expired"` the payload must not carry `command` or `mutation`; a draw alert (no `cause`) still must. A payload that mixed them validated in 0.4.0 and is now refused.
- **`raiseUnits` no longer guesses units.** 0.4.0 rejected an `at` and a cycle bound whose magnitudes differed by 100 times or more, which also rejected small synthetic instants (`at=5` with `cycleEnd=1000`). It cannot see units, so `at`, `cycleStart` and `cycleEnd` must all be milliseconds. `perUnit` stays a whole number (menu allowances are whole). `prorationPair` calls your `isTierPrice` once per proration line, where 0.4.0 called it about three times.
- **`env` is validated once** at each public entry point (`handleStripeWebhook`, `handleStripeEvent`, `menuCatalogRows` and the grants functions) and passed down resolved: a bad value throws before anything else runs, including on the grants functions' no-op paths, and can no longer be answered as `missing_metadata`.
- **One customer, several subscriptions: what atm supports (checked in the Stripe sandbox, 2026-11-05).** A person can be a member of several schools: one Stripe customer held three active subscriptions, and atm kept each school's subject apart by `b4u_school` and `family_id` in the subscription's metadata. Three limits to know:
  - **Route by school.** One `handleStripeWebhook` serves one school (`WebhookDeps.schoolId`). If several schools share one Stripe account and one endpoint, read `b4u_school` from the event's metadata and call that school's handler. An event for another school answers 422 `school_mismatch`, which Stripe retries, so a handler fed every school's events will fail every other school's. With one Stripe account per school nothing needs routing.
  - **A subscription that holds only a recurring add-on grants nothing.** An add-on is attached from the tier subscription's own create or renew invoice, or from a mid-cycle `subscription_update` invoice of that subscription. An invoice for a separate add-on-only subscription is recorded as decided with no credits (the handler answers `applied`), so the member pays and gets none. Cancelling that subscription would not retire the add-on either, because the membership follows one subscription. Put add-ons on the tier subscription.
  - **One tier subscription per school and family.** Events about another subscription of the same family and school do not change the membership, and a second tier subscription after the first ended throws "a second subscription for the same family is not supported yet".
  - The Stripe billing portal lists every subscription of a customer with its own update link, but names them by product only, so two schools' `Sparkle` look alike in a shared account. A subscription with only an add-on gets "Cancel" and no update link.

## Moving to 0.4.0 from 0.3.0

Everything is additive: a 0.3.0 caller that changes nothing gets the same rows, keys and events. What is new, and what a caller has to do to use it:

- **The raise rule as functions.** `prorationPair` reads Stripe's pair of proration lines and `raiseUnits` turns a raise into the units to grant; `invoiceToCommands` calls their unchecked cores (since 0.5.0), so the webhook never throws on a Stripe value. The public functions now throw an `Error` naming the field on bad input (not a finite number, a negative or fractional count, `cycleEnd` before `cycleStart`) instead of returning a wrong number (0.4.0 also rejected a cycle in seconds against `at` in milliseconds; 0.5.0 no longer guesses units, see below). A yearly raise grants the prorated year (a raise 2 to 4 ninety days in grants 19), not 0. The baseline is `GrantsState.quantity`, what the credits reflect, not Stripe's count: pass that to `raiseUnits`.
- **`portalConfigOf(menu, { products, prices })`** makes the billing portal configuration for a tier sold in quantities (a raise billed at once, a decrease at the renewal). A member who also holds a recurring add-on is not offered the update by the portal, whatever the configuration lists (checked in the sandbox), so the caller needs its own route for them. See `README.md`, "Billing portal".
- **Importing a caller's own rows.** `grantsStateFromCallerRows` turns a caller's existing lots into atm's rows and `GrantsState` (see "Moving an existing caller onto `handleStripeEvent`" below); it throws, naming every problem, rather than guess.
- **`env`.** `handleStripeEvent`, `handleStripeWebhook` (as `WebhookDeps.env`) and `menuCatalogRows` take an optional `env` (`"live"` or `"test"`, default `"live"`; anything else throws). It is part of the subject key, `<school>|<env>|family:<id>`. A school with a Stripe test endpoint and a live one must pass it, or both land on the live subject. The family service has `billingKeyMode` and has to pass that. The handler's claim, invoice index, payment index and outbox keys carry no env: Stripe's ids differ between modes, so two endpoints sharing a database do not collide, but the same id under both would be claimed once (closing it changes the DDL; `ROADMAP.md`, and `docs/log-and-r2.md` under "Env on the handler's tables").
- **Expiry alerts.** `lapseAlertEvents` makes a `credit.depleted` (payload `cause: "expired"`) when a lapse takes a feature's credits from above 0 to 0, one per instant however many rows lapse then. Calling it is the opt-in; `lapseEvent` is unchanged. Since 0.5.0 it takes `drawnAfter(instantMs)`, the units the holder drew after an instant, because the state holds balances as of now and a late run would otherwise judge a past lapse on credits drawn from another row since (see "Moving to 0.5.0 from 0.4.0"); `() => 0` is right only when the state is as of the lapse, the state the cron gave `lapsedRows`. A row made after the lapse is still counted, since the state does not record when a row was made. There is no `credit.low` on a lapse.
- **Replay** reads logs written by 0.3.0 and stops at what they lost (see "Replaying a log" below). **Invoice links and the one-time checkout** are described under "Invoices and receipts" below. An endpoint left on an API version older than `2025-10-29.clover` has its b4u invoices refused with 422, which Stripe retries; the dashboard is the only signal.

## Moving to 0.3.0 from 0.1.0

0.1.0 was the engine as a CLI and a library: `runEngineCommand` and the engine's own types, nothing else. Everything billing-related is new to a 0.1.0 caller: the menu, Stripe mappings, grants, the webhook handler, the object store and the ledger events. `runEngineCommand` and the CLI work as before. `README.md` describes each piece; this lists what a caller has to provide and the behaviours that are easy to get wrong.

### Stripe

- **API version.** The mappings read Stripe API `2025-10-29.clover`; an event from any other version is refused (`unknown_mapping`), with a message that names the endpoint's version (`event.api_version`) and the fix, which is to recreate the endpoint with `api_version: "2025-10-29.clover"`. atm does not read a second layout (an older endpoint sends `line.price.id` and `line.proration`): the mappings are checked against the pinned version's OpenAPI spec, and a second shape would be unchecked. A school's webhook endpoint must be created with `api_version: "2025-10-29.clover"` (the endpoint's version, not the request header, decides the shape of the events it receives), and every API call should send the same `Stripe-Version`.
- **Events to subscribe to:** `invoice.paid`, `invoice_payment.paid`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `charge.refunded`, `charge.dispute.created`, `charge.dispute.closed`, and since the section at the top `payout.paid`. Without `invoice_payment.paid` a refund or dispute cannot find its invoice and answers 409 until Stripe gives up.
- **Checkout metadata.** Put `b4u_school` and `family_id` in `subscription_data.metadata`. On the invoice they arrive at `parent.subscription_details.metadata`; atm reads both and the invoice's own keys win.
- Shapes were checked against real payloads from a Stripe sandbox (`fixtures/billing/stripe/recorded/`). The pin is still unverified against a school's own account.

### Handling an event

- **One entry point:** `handleStripeEvent(input)` turns a raw Stripe event and the subject's stored rows into row changes and ledger events. It reads no clock and writes nothing. The caller verifies the signature, dedupes on Stripe's event id, checks the revision and writes the result in one transaction.
- **`eventId` must be a ULID**, the id of the stored input event, not Stripe's `evt_` id. Anything else comes back `refused` as `bad_event`. Derive it from the Stripe id with `deterministicUlid` (exported from `atm`) so a replay gets the same id. The reference handler uses:

  ```ts
  const eventId = deterministicUlid({ timeMs: event.created * 1000, revision: 0, seed: JSON.stringify([schoolId, event.id]) });
  ```

  `timeMs` is the event's own instant (Stripe's `created` in milliseconds); `revision` is the subject's revision, or `0` as here (it fills 24 bits of the id so events in one millisecond sort in the order they were decided); `seed` is any string that is stable for the event and unique to it across schools (the handler seeds with its canonical JSON of `[schoolId, stripeEventId]`). The same three inputs always give the same id.
- **Reference handler.** For Bun or Node, `handleStripeWebhook(deps, request)` verifies the signature, claims the event id in its own short transaction (a stale claim is taken over), then writes rows, events, the indexes and the done mark in one SQLite transaction. Create its tables with `HANDLER_DDL`. A caller with its own handler must provide the same three things: the claim, the invoice-to-subject index and the payment-to-invoice index.
- **One school per endpoint.** `deps.schoolId` is required: the school this endpoint and its signing secret belong to. An event whose `b4u_school` names another school is refused (422 `school_mismatch`) before anything is claimed.
- **Answers.** What Stripe sees decides whether it retries, so the handler sorts every outcome into one of three kinds:

  | Answer | Outcome (`reason`) | Meaning |
  | --- | --- | --- |
  | 409, retryable | `refused` (`unmatched_invoice`), `refused` (`unknown_subscription`), `unmatched_payment`, `busy`, `stale_revision` | The link or the earlier event has not arrived yet, or another delivery holds the claim. Stripe retries; nothing needs fixing. `unmatched_payment` is its own outcome (a refund or dispute whose payment is not in the payment index yet), not a refusal reason. |
  | 422, needs a human | `refused` (`unmatched_line`, `missing_metadata`, `unknown_mapping`, `bad_event`, `rejected`), `unknown_school`, `school_mismatch`, `livemode_mismatch`, `ambiguous_payment` | Retrying gives the same answer. `missing_metadata` is metadata that is half filled (for example `b4u_school` without `family_id`); `unknown_mapping` is an event from another API version; `unknown_school` is a school with no context; `livemode_mismatch` (0.5.0) is an event whose `livemode` disagrees with `env`; `ambiguous_payment` is a payment that links to more than one invoice. |
  | 200, done | `applied`, `duplicate`, `ignored` | `ignored` is an event type atm does not handle, and an event with no `b4u_school` at all (not one of ours, for example another product on the same Stripe account). |

  A 401 (`bad_signature`) and a 400 (`bad_request`) answer a delivery that never reaches the rules.

### Credits

- **Deduction order.** Put `commandOrg(policy)` on every `track`, `check` and `finalize`. `policy.deductionOrder` is `expiry` (default: the row that lapses soonest first, then the oldest grant) or `engine` (Autumn's own order). A caller that sends its own org config gets the engine's order.
- **Stored state.** A subject's billing state is one JSON row (`atm_grants`) beside the engine's rows, under the same revision. It holds each grant's `holder` and `retired` flag and the subject's `membership`.
- **Membership status** has the value `incomplete` (not yet paid), and `customer.subscription.*` events record the membership without granting anything: credits still come only from paid invoices.
- **Policy.** `deductionOrder` and `lowCreditThreshold` are policy fields; a school's policy that leaves them out gets the defaults.

### Events

Ledger event types include `credit.expiration_changed` (a row's credits stay but their end date moved), `credit.low` and `credit.depleted`. Delivery of "N visits left" notices stays with the caller.

- `credit.low` and `credit.depleted` fire only for draws by `track` or `finalize`, that is customer activity (holds and spends). A refund or dispute clawback and an admin edit do not raise them. The one other source is the clock: a cron that calls `lapseAlertEvents` gets a `credit.depleted` (`cause: "expired"`) when rows lapse and the feature's total goes to 0.
- They are judged on availability including holds, so a hold can take a family under the threshold before any visit is spent.
- atm does not remember that it already alerted. The family service should dedupe its notices per holder, feature and grant or cycle.
- They are opt-in per call. `handleStripeEvent` never makes them (it runs only billing commands). The family service passes `policy.lowCreditThreshold` as `lowCreditThreshold` in the context it gives `mutationToEvents` for its own `track` and `finalize` mutations. Without it no alert is made at all; a threshold of 0 makes `credit.depleted` only.

### What surprised us on real Stripe data

These are facts about the API at `2025-10-29.clover`, checked against sandbox payloads. They are why the mappings read what they read.

- A subscription's tier and interval come from its price items (`SubscriptionFact.items`: price id, lookup key, interval), not from checkout metadata, which goes stale after a plan change in the portal.
- A real charge carries no refund list. `BillingRefund.id` is the Stripe event id and `amount` is the charge's total refunded after the event.
- A renewal invoice's own period is the previous one. The renewal's period comes from the tier line.
- With checkout's `subscription_data.metadata` the invoice's own metadata is empty; it is on `parent.subscription_details.metadata`.
- A charge or dispute does not name its invoice; `invoice_payment.paid` is what links them.

### Tier quantities

A studio sells one tier at several counts (Vibes of Light: Shine at 1, 2 or 4 sessions a month) with `quantities` on the menu tier instead of one tier per count.

- **Menu.** `MenuTier.quantities`: 1 to 6 unique whole counts from 1 to 50, ascending; absent means `[1]`. Prices and grant amounts are per unit. A price times its largest count must stay under 99,999,999 (Stripe's line cap). Editing `quantities` makes no `menuToStripe` step.
- **Checkout.** `checkoutParams` takes `quantity` (default 1). A count the tier does not offer comes back `{ reason: "quantity_not_offered", quantity }`; answer 400 with `fields: ["quantity"]`. `line_items` is now a tuple: the tier line first (at the quantity), add-ons after at 1. The subscription metadata carries `quantity` only when it is not 1, and only for information: the item's quantity at Stripe is the truth.
- **Normalized events.** Subscription items and invoice lines carry `quantity` (an integer 0 to 99,999,999; a missing one reads as 1; a negative, fractional or larger one is refused `bad_value`). A line or item with quantity 0 is dropped by the grants rules, never counted as 1.
- **State.** `GrantsState.quantity` is what the credits reflect and moves only with paid invoices; `MembershipRecord.quantity` is what Stripe says and moves with `customer.subscription.*`. A stored state from 0.2.0 loads with both at 1.
- **Credits.** Create and renewal grant the per-unit allowance times the tier line's quantity (a yearly payment on a monthly grant: times 12). A raise on the same tier grants the extra units, prorated per `policy.upgradeGrant`, counted from the quantity the credits reflect (`GrantsState.quantity`), not from Stripe's old count: after a decrease that waits for the renewal, a raise back up to the count the credits still hold grants nothing, and one above it only the units past it. A decrease grants nothing and takes effect at the renewal. Rollover `max` scales with the quantity, and the engine has one cap per row, so after a decrease the carry-over cap follows the lower count.
- **The rule without the state.** A caller that keeps its own credits and has no `GrantsState` reuses the raise rule instead of copying it: `prorationPair(lines, isTierPrice)` reads Stripe's pair of proration lines and `raiseUnits({ perUnit, oldQuantity, newQuantity, at, cycleStart, cycleEnd, policy })` gives the units to grant (README, Billing, "Quantity raises without the grants state"). `invoiceToCommands` calls both. Pass the quantity your credits reflect as `oldQuantity`.
- **The family service must:** make a raise with `proration_behavior: "always_invoice"` (otherwise Stripe bills it at the renewal and nothing is granted until then); schedule a decrease for the renewal; and read `quantity` from the subscription item, not from metadata. `portalConfigOf(menu, { products, prices })` (added after 0.3.0, so not in that tarball) makes both settings for the billing portal: post its fields to `/v1/billing_portal/configurations` and pass the id it makes as `configuration` on each portal session (`README.md`, "Billing portal"). It returns `null` for a menu without quantities, where the school's default portal applies. A caller that changes quantities through its own API calls instead must set `always_invoice` and the scheduled decrease itself.
- A tier change and a quantity change in one update grant `newAmount x newQuantity - oldAmount x oldQuantity`, not below 0. This case is not checked against real payloads.
- **A raise on a yearly plan grants too** (it does not grant 0). A monthly grant on a yearly plan counts 12 per unit, so the extra units carry a year of it, prorated per `policy.upgradeGrant` by the share of the year left (2 -> 4 of a 2-a-month tier, ten days in: 2 x 12 x 2 = 48, x 355/365, rounded up: 47; `full` 48; `none` 0). A yearly grant on a monthly plan (a retreat a year) grants nothing at a raise: its next refill is already at the new count. Only synthetic fixtures pin this; no real yearly raise payload has been recorded.

### Invoices and receipts (after 0.3.0)

What a family service caller changes:

- **Link a receipt.** `BillingInvoice` has `number`, `hostedInvoiceUrl` and `invoicePdf` (`string | null`, absent on a fact built by hand). `handleStripeEvent`'s result does not carry them (the grants state keeps no invoice facts), so read them from `normalize` of the same `invoice.paid` event (or from the raw event), then store or show the number and the two links. The URLs are bearer links: give them only to the family the invoice belongs to and keep them out of logs.
- **Selling a gift certificate or a pack with no membership.** Do not build the Checkout by hand in `mode=payment` without `invoice_creation`: Stripe then makes no invoice and no `invoice.paid` arrives, so nothing is credited. Call `oneTimeCheckoutParams` (it returns payment-mode parameters with `invoice_creation[enabled]=true` and our metadata in `invoice_data.metadata`), then `withPriceIds` and `toStripeForm`, as you do for a membership. The webhook endpoint is the same (`invoice.paid`). A one-time add-on bought together with a membership needs nothing new: it rides the subscription's first invoice, as before.
- **`checkoutParams` is unchanged.** Same output for the same input; still subscription mode only. `withPriceIds` now also accepts `oneTimeCheckoutParams`'s result (typed by overload; a membership's call still returns `CheckoutParamsWithPrices | null`).
- **School setup, not code.** The invoice shows the school's name, address, branding and tax ID from the school's own Stripe account (the connected account is the issuer of a direct charge). The EIN prints only if the school has it as a tax ID on that account (`us_ein`) and as a default account tax ID. Idaho's itemised receipt also needs the child's legal name, subject, hours and tax, which the Stripe invoice does not hold; atm does not build that receipt yet (`ROADMAP.md`; the open questions are in `docs/receipts.md`).

### Storage

- `Store` and its errors, `FolderStore` and `R2Store` (on `aws4fetch`) are exported, with a contract suite that runs against the folder and SeaweedFS. Live balances stay in the caller's SQLite; the object store holds the append-only log.
- Both stores validate keys and byte ranges strictly and refuse what they cannot serve; no caller should rely on a looser reading. `FolderStore` treats reserved names case-insensitively, as a case-insensitive filesystem does.
- `balance-engine` has one opt-in change (`org.config.deduction_order`), listed in `UPSTREAM.md`.

### Moving an existing caller onto `handleStripeEvent`

For a caller that already grants credits on its own and has paying members (B4 Uni's family service: `school_memberships`, `school_credit_lots`, rules in `src/school-billing/grant.ts`). It uses only `runEngineCommand` today; this is how to move it onto `handleStripeEvent` without regranting anything.

1. **Create each school's webhook endpoint with `api_version` `2025-10-29.clover`** (see Stripe above). An event from any other version is refused (`unknown_mapping`) with a message that names the endpoint's version and says to recreate it.
2. **Import each member once**, in one transaction, with the member's lots and the menu their invoices were granted against:

   ```ts
   const { state, rows } = grantsStateFromCallerRows({ membership, lots, menu, now });
   // write `rows` (engine rows and the atm_grants row) for the subject <school>|live|family:<family_id>, at one revision
   ```

   `membership` and `lots` are the `SELECT *` rows (`CallerMembershipRow`, `CallerCreditLotRow`): the membership's instants are Unix seconds, the lots' are milliseconds. `now` is the instant of the import: a lot past its `expires_at` holds nothing and is not carried over. The subject is `family:<family_id>` at the membership's school, the identity the caller already uses.
3. **Stop the caller's own grants and takebacks at the same moment** (the `grantForInvoice` and `removeForInvoice` calls), and hand `handleStripeEvent` only events the caller has not applied: an invoice the caller granted is found in `state.invoices` and grants nothing, but an event the caller handled that left no lot (an upgrade proration, a manual invoice) is not known to atm and would be decided afresh. Start from the caller's `school_stripe_events` cutoff.
4. **Pass `invoiceIds` for payments made before the import.** A refund or dispute names its charge and payment intent, not its invoice; atm learns the link from `invoice_payment.paid`, which it has not seen for the old invoices. Without it a refund of one of them is refused `unmatched_invoice` (409, retried until Stripe gives up). The caller has the link (the invoice's `payment_intent`). The reference handler finds the subject of a refund by joining two tables, so each old invoice needs a row in both: `atm_payment_index` (payment intent to invoice id) and `atm_invoice_index` (invoice id to the subject key, `<school>|live|family:<family_id>`). With only the first, the refund is answered 409 `unmatched_payment`.

What the import reads from the rows, and what it does not:

- **Read:** the holder (`school_id`, `family_id`), the subscription, the tier, interval and add-ons, the quantity the credits reflect (the newest tier lot's `allowance` over the menu's per-unit amount; the membership's own `quantity` goes to `membership.quantity`), the cycle (read back from the lots' `expires_at`, minus the rollover months on the school's calendar), each lot's balance, expiry and removal, and the decided invoices.
- **Refused, naming each problem** (one error lists them all): a tier, add-on or feature the menu does not have; a tier the menu does not price at the membership's interval; a lot that is no grant of the membership's tier, or is for an add-on the membership no longer has; a lot of another member or with a source that is not `tier` or `addon:<id>`; a tier grant or a recurring add-on with no lot (atm refills only rows it holds, so it would silently stop granting it); credit rows on different cycles (a renewal granted to some and not others); a lot that is not a whole number of the menu's per-unit amount. A membership with no lots yet imports as just the membership: the first invoice then grants as for a new member.
- **Not in the rows (the owner decides):**
  - `GrantsState.anchor` (the first invoice's period start) is `null`; no rule reads it.
  - `cycleStart` is the cycle end minus one interval, not the invoice's own start; only the proration of a mid-cycle upgrade reads it.
  - A yearly grant on a monthly plan (Shine's retreat) has no refill date in the rows: its next refill is set a year after its lot's creation. The caller's own rule gives such a lot `expires_at` = the end of the first month's period (it has no rollover), so by the second month the lot holds nothing and the import carries that balance of 0; atm then refills it a year after the first invoice. Decide whether the retreat should be restored for current members.
  - `GrantsState.tierId` is the membership row's tier. A plan change Stripe made that no invoice has paid yet cannot be told apart in the rows.

Where atm's rules differ from the caller's, so a renewal after the import is not always the same (each is pinned in `tests/billing-adopt.test.ts`):

- **Rollover cap.** The caller never caps a rollover (a lot keeps its balance until it expires); atm carries over at most the grant's `rollover.max` (times the quantity). A leftover above the cap is lost at the renewal. The imported rows themselves are not capped.
- **Rollover months on the school's calendar.** The caller adds rollover months on the school's time zone; the engine adds them on the UTC calendar. Across a clock change the rollover of a cycle lapses a whole hour from the caller's lot (Denver, a January cycle: 17:00Z against 18:00Z).
- **A cycle not renewed.** The caller's lot lapses at the cycle end plus the rollover months. atm's refilling row stays until the next invoice or the cancellation (`subscriptionEndedToCommands` sets its expiry).
- **Session gifts.** The caller's gift lot lasts until its own rollover months, or keeps if the grant has none; atm gives a gift of sessions an expiry `policy.giftSessionMonths` after payment (six months by default). Gifts imported keep the caller's expiry; a gift bought after the import gets atm's.
- **What an invoice grants.** The caller grants on `subscription_create`, `subscription_cycle` and `subscription_threshold` only. atm also grants a mid-cycle upgrade or a raise in quantity (a `subscription_update` invoice, per `policy.upgradeGrant`), which the caller does not.

### Replaying a log (after 0.3.0)

`replayEvents` now reproduces what `handleStripeEvent` writes. What a caller needs to know:

- **New events.** `handleStripeEvent` records every event of a command with the whole mutation (`payload.slice` lists the positions in `mutation.changes` an event is made from, when one mutation is booked as several events by feature and plan, so `payload.mutation.changes` is no longer the event's own part), a command that moves no credits as a `plan.changed` with no postings, and `payload.complete: true` on every one of them. The envelope and the event types are unchanged; the payload schemas gain optional `slice` and `complete`. A caller that ships `result.events` as they are changes nothing; one that reads `payload.mutation.changes` of a `credit.*` event as that event's own changes must read `payload.slice`.
- **Order.** A subject's commands replay in revision order, not id order (a reset runs at the start of the period it refills, so its id can sort before the plan at payment time). `lastEventId` and `snapshot.lastEventId` are places in that order: pass the same events each time.
- **Revision gaps.** The stored revision also moves on a write of the grants row alone (a dollar gift, a membership event). For a log whose writer marked `complete`, replay reads the next mutation's `revision.before` and steps over the gap. `complete` is a claim by the writer, not something replay can check: a log writer that sets it on a log that lost a command, or a middle event deleted from a `complete` log, replays with no `ReplayGapError` and no `lossySubjects`. Keep the log append-only and write `complete` only from `handleStripeEvent`.
- **Logs written by 0.3.0.** They have no `plan.changed`, no `slice` and no `complete`, and a mutation booked per feature holds only each event's own changes. Replay reads them: it reassembles a mutation from the events that name its `mutation.id`, runs the recorded command in the engine, and checks the changes the log holds against the engine's (all of them when the log has all, else that each is among the engine's). What it cannot do is invent a command the log does not hold. 0.3.0 did not log the cycle-end update after a renewal (an `applyBillingPlan` that puts a refilled row's next reset on Stripe's cycle end; it changes a row only after a month end, Jan 31 to Feb 28 to Mar 31, and is a no-op otherwise), and a write of the grants row alone leaves the same revision gap, so the two cannot be told apart. Therefore:
  - a log with no revision gap replays, and its result has `lossySubjects` naming each subject whose last handler command was written by 0.3.0: the command the writer ran after the last one logged, if any, is not in the replayed rows;
  - a log with a gap stops at the first event after it with `ReplayGapError` (exported from `atm`; a `ReplayError` with `eventId`, `gap: { subject, after, before }` and `prefix`, the replay of everything before the gap, snapshot and balances). The message says the log was written by 0.3.0 and cannot be rebuilt past that point. Rebuilding past it needs the rows as the handler stored them at that revision, which the log does not hold;
  - a log of 0.3.0 events followed by current ones replays through when no command was lost between them, and stops with the same error at the boundary when one was.
- Nothing rewrites stored events. Handler events of a subject that is carried on after the upgrade are the current shape from the first write on.
